# 无线唤醒可选能力：BLE 周期广播（PA） / ESP-NOW

> **定位：PA 是已实施的无线唤醒能力，但不进 §六 的深睡档基线（25~65µA @24V）——
> 它是**另一档**功耗（亚 mA，按 T 分档）。**
> 数据来源：`ESP32_wakeup_by_BLE_adv` 仓库下两个独立实验——`tests/ble_sync`（PA）与
> `tests/espnow_wakeup`（ESP-NOW）。全部为合宙 CC 电流表**逐包均值**口径的实机实测。
> 本文自包含，不依赖该仓库。

---

## 0. 为什么无线唤醒必然打破 µA 级待机

本板基线的 **25~65µA @24V（≈0.6~1.56mW，见 `doc.md` §六）** 建立在**深睡 + 本地感知**（编码器 INT / RTC / 干接点）之上。
任何"靠射频监听唤醒"的方案都绕不开一个物理约束：

> **ESP32 全系芯片在 deep sleep 期间，Wi-Fi / BLE 控制器无法保持接收。**
> （v3.3 / v4.4 / v5.1 三代源码验证）

⇒ 要能收到唤醒包，芯片必须停在 **light sleep**（modem sleep + 射频按窗口开启）。
⇒ **轻睡地板是 mA 级**，这正是 §五.6 已经写明的那句：

> 唤醒收发器要付出 mA 级电流，是 µA 级待机的**几十倍**

**所以本文两条路线都不与深睡档基线竞争。** 它们的定位是：**需要远程触发时才启用**的可选能力，
启用期间待机从 µA 级升到亚 mA 级（PA）或 mA 级（ESP-NOW）。

**这在工程上是可接受的**——手拉/本地感知仍是主路径，无线唤醒用于
"人不在现场但要远程操作"或"与网关/中控联动"的场景。

## 1. 两条路线的实测模型

### 1.1 BLE 周期广播（PA）—— 实测于 ESP32-C6

PA 让接收端建立**周期同步**，从而拿到精确锚点，**收包调度由控制器自行完成**：

```text
I_RX = f + 0.160 / T          T = PA_interval × (skip+1)
I_TX = f + 0.134 / PA_interval        ← 发射端不能 skip
最坏响应 ≈ T
```

| 量 | 实测值 | 含义 |
| --- | ---: | --- |
| **C_RX** | **0.160 mA·s** | 接收端每次唤醒的电荷成本 |
| **C_TX** | **0.134 mA·s** | 发射端每次唤醒的电荷成本 |
| `f` | **约 0.06 mA**（定制板 + 32.768kHz 晶振，含芯片轻睡 34µA + 板级） | 地板 |

> **对比基线**：legacy BLE 被动扫描的每次唤醒成本 ≈ **5.1 mA·s**。
> **PA 便宜约 32 倍**——因为它免除了"扫描窗口必须 ≥60ms"这个前提
> （legacy 广播在 37/38/39 三信道轮转，接收端不知道相位，窗口必须覆盖一次完整轮转）。

**关键**：C 已被证实由控制器固定的 `BLE_RTC_DELAY_US_LIGHT_SLEEP = 3200µs` 主导，
**不是收包本身**。所以它是个常数，不随包长/内容剧烈变化——也因此**降发射功率无效**
（实测 −9dBm 只让 C_TX 降 2%）。

### 1.2 ESP-NOW —— 实测于 ESP32-S2

两套架构，实测模型：

```text
架构① 深睡 + 周期开窗:   I ≈ 0.44 + 4.42 / T(s)   mA    响应最坏 = T + ~40ms
架构② 轻睡常驻:          I ≈ 4.96 + 39.5 × duty   mA    响应最坏 = interval
```

| 量 | 实测值 | 含义 |
| --- | ---: | --- |
| 架构① 深睡平台 | 0.081 mA（S2 板） | 81 µA |
| 架构① 每次唤醒 | **4.42 mA·s**（≈92ms 窗口 @55.3mA） | 其中 `wifi_init` 固定 ~32ms |
| 架构① 60s 档 | **0.25 mA** | 报 0.14~0.30 区间 |
| 架构② 地板 | **4.96 mA** | Wi-Fi 驱动 + connectionless PS 的固定开销 |
| 架构② 斜率 | 39.5 mA / 单位占空比 | 射频监听成本 |
| 两架构交叉点 | **(6.1 mA, ~0.9 s)** | <0.9s 用架构②，≥0.9s 用架构① |

## 2. 核心对比：每次唤醒的成本差 32 倍

**这是两条路线最本质的差别，也是选型的决定性因素：**

|  | 每次唤醒电荷成本 | 说明 |
| --- | ---: | --- |
| **BLE PA** | **0.160 mA·s** | C6 实测 |
| ESP-NOW 架构① | **4.42 mA·s** | S2 实测（92ms 窗口，含 wifi_init 32ms） |
| legacy BLE 扫描 | ~5.1 mA·s | C6 实测（60ms 窗口） |

在**给定时延预算 T** 下，唤醒频率 = 1/T，所以"每次唤醒成本"直接决定功耗：

| 最坏响应 T | PA（C6，`f`=0.06） | ESP-NOW 架构①（S2，`0.44`+4.42/T） |
| ---: | ---: | ---: |
| 0.2 s | **0.86 mA** | 22.5 mA |
| 0.5 s | **0.38 mA** | 9.3 mA |
| **1 s** | **0.22 mA** | 4.9 mA |
| 5 s | **0.09 mA** | 1.3 mA |
| 60 s | **0.063 mA** | 0.51 mA（实测 0.25） |

**⇒ 在 1 秒及更短的响应预算下，PA 比 ESP-NOW 好 20 倍以上**，根源就是那 32 倍的每次唤醒成本差。

> ⚠️ **上表跨芯片比较，只能看趋势不能看绝对值**（见 §4）。

## 3. 选型建议

| 需求 | 建议 |
| --- | --- |
| **最坏响应 ≤ 1 s** 且要求待机尽量低 | **BLE PA** —— 单端 0.22 mA，ESP-NOW 同预算是 5 mA 级 |
| 最坏响应 ≥ 5 s，追求最低待机 | 两者接近；PA 略优（0.06 vs 0.09 mA/端），但差距不大 |
| 需要**有确认的链路**（TX 知道唤醒是否送达） | ESP-NOW（自带 ACK）；PA 需 PAwR 才有 ACK，代价 +80% 电流 |
| 需要**发射端也电池供电** | PA（发射端 0.13 mA·s/次，实测） |
| 需要**与现有 Wi-Fi 中控/路由器组网** | ESP-NOW |
| 需要同时跑 Wi-Fi 业务 | ESP-NOW（PA 与 Wi-Fi 共存可行但需验证） |

**对本板的具体建议**：

- 本板有 **32.768kHz 晶振**（§五.5 已设计）—— 这是 PA 路线的**硬前提**（见 §4）。
  板上已有，等于入场券已经拿到。
- 本板主控是 **ESP32-C6** —— 正是 PA 实测用的芯片，数据可直接用。
- 若无线唤醒只用于**偶发远程操作**，且可接受 1s 级响应 → **选 PA**。

## 4. ⚠️ 必须知道的前提与未验证项

### 4.1 PA 路线的三条硬前提

| # | 前提 | 状态 |
| --- | --- | --- |
| 1 | **32.768kHz 晶振** | ✅ 本板已设计（§五.5）。若无晶振，用主晶振做休眠时钟要多 **3.33 mA**（实测） |
| 2 | **主控用 C6** | ✅ 本板即 C6。实测 C6 的每次唤醒成本约为 **C3 的一半**（RX 0.16 vs 0.326；TX 0.134 vs 0.246 mA·s） |
| 3 | **`f` 地板达标** | ⚠️ 本文取 `f`=0.06mA（假设：芯片轻睡 34µA + 板级 ~30µA）。**板级部分需按实际设计核算** |

### 4.2 跨芯片比较的局限

- **PA 数据来自 C6** → 与本板同芯片，**可直接用**（前提是晶振就位）
- **ESP-NOW 数据来自 S2** → **不能直接搬到 C6**。其中：
  - 深睡 0.081mA 是 **S2-Pico 板**的值；本板 C6 深睡档按 §六 是 **25~65µA**（已计入 TVS 高温漏电）——**板级同量级**，不能据 0.081mA 推出本板深睡档更低
  - 架构②的 4.96mA 地板是 **S2 的 Wi-Fi 地板**；C6 的 Wi-Fi 地板**未实测**
- ⇒ 上表 §2 的 ESP-NOW 列**高估**了它在 C6 上的表现（尤其长周期档）。
  **要做 C6 上的公平比较，需在 C6 上重跑 ESP-NOW。**

### 4.3 其他未验证项

| 项 | 说明 |
| --- | --- |
| **ADI（PA 增强）** | 实测可再省 ~9%（T=1s）：接收端每次唤醒的 host 侧成本 0.0204 mA·s，占 C_RX 的 13%；而 `filter_duplicates` 只在数据变化时才打扰 host，**契合"唤醒端常态是无事件"**。⚠️ **只有 C6 支持**；且要求发射端只在真事件时递增 DID（**架构改动**） |
| **PAST** | 用连接转移同步、免去发现扫描。本场景无连接，**判定价值低**（除非有常电网关） |
| **PAwR** | 无连接的 ACK。**用功耗买可靠性**——RX 回一个 response 要 +`C_TX`，相对 `C_RX` 是 **+80%** |
| **长稳失步率** | 只观察了分钟级（60s 内零失步）。**数小时 soak 未做**——它决定 PAST 是否值得 |
| **深睡下 32k 晶振的电流增量** | 见 §九 待核实 #3。补注：**深睡下 BLE 不活跃、主晶振不参与**，所以深睡时晶振的增量应是**振荡器本身的 µA 级电流（1~3µA 量级）**，不会是 mA 级。⚠️ 这是推断，仍建议实测确认 |

## 5. 与本板 §六 唤醒源表的衔接

**决策：采用 PA**，并已接入固件（平台层 `code/components/focstep_platform/src/pa_wake.c`；
实现、纪律与上板验收见 **`code/README.md` §13**）。ESP-NOW 不采用（每次唤醒贵 ~28 倍）。

| 唤醒源 | 机制 | 待机功耗 | 状态 |
| --- | --- | --- | --- |
| **BLE 周期广播（PA）** | 周期同步 + 窄窗口，收包调度由控制器自理 | `f + 0.16/T`：T=0.5s → ≈0.4mA；T=3s → ≈0.11mA（C6 实测模型，`f` 待实测） | ✅ 已接入 |
| WiFi/ESP-NOW | 轻睡数据包唤醒 | **4.96 mA 地板**（S2 实测，`4.96 + 39.5×duty`） | ❌ 不采用 |

⇒ **待机口径变成三档**（§六 已同步）：
① **深睡档**（无线关 / 监听窗口超时回落）≈**25~65µA ≈ 0.6~1.56mW@24V**（`doc.md` §六），只能本地唤醒；
② **PA 监听档**（出厂默认上电即监听）＝ **亚 mA**，按 T 分档；
③ 运行态（电机主导，同步保持）。**写出厂指标必须注明档位。**

**采用的默认参数**：T = 0.5s（发送端被运动唤醒时）/ 3s（倒计时无动作，可由发送端指令动态改）；
出厂"上电即监听 + `FOCSTEP_PA_LISTEN_HOLD_MS`（默认 10 min）无活动则回落深睡档"。
⚠️ `f` 与实得 T（240ms 间隔下 0.5s 落成 **480ms**、3s 落成 **3120ms**）都**必须上板实测**。
